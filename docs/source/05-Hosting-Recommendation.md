# 1. The answer in five lines
- Recommended setup: AWS Mumbai "hybrid". One small AWS server (EC2) runs the app exactly as the developer already packages it (Docker); the data sits in a managed database (Amazon RDS for PostgreSQL 16) with a rewind button; files and backups go to Amazon S3. Everything is in Mumbai, with backup copies in Hyderabad. Keep the Vercel copy in Singapore as a sample-data demo only.
- Monthly cost today (20 to 50 users, 300 documents a day): US$85.69, which is Rs 8,158 before GST and Rs 9,627 with 18% GST. This is the reviewer's US$72.04 (Rs 6,859; Rs 8,093 with GST) plus US$13.65 for a small monitoring server that the operations review requires (an estimate of mine, section 4). First months are cheaper, about US$79 to 84. A GST-registered company can normally claim the GST back; confirm with your chartered accountant.
- At 3x (60 to 150 users): US$221.40, Rs 21,077 (Rs 24,871 with GST), mainly because the database becomes a two-zone, always-on pair; about US$155 if you keep it single-zone. At 10x (200 to 500 users): US$439.67, Rs 41,857 (Rs 49,391 with GST), or US$613.20 (Rs 58,377) on full AWS with spare capacity.
- Why not Vercel: it is not wrong, but for real data it is second choice. Rewinding the database to any minute costs a flat extra US$100 a month there; the file-size limit (4 MB) breaks phone photos and bank-statement PDFs; the "every 15 minutes" chores run once a day unless reworked; and Vercel does not say where its logs and build records live, so "all data in India" cannot be promised. Vercel plus Supabase costs US$164.75 a month today (Rs 15,684) against US$85.69.
- Why not full AWS containers (ECS) yet: it costs US$225.48 a month today (Rs 21,465) for spare capacity Radboards will not use for a year or more. The recommended setup is built so the later move touches only the app, not the data, and needs no data copy.
How sure: the choice is real but close. On the reviewer's scoring the recommendation gets 4.00 out of 5 against 3.75 (Vercel) and 3.70 (full AWS). The weights decide the winner; section 3 says which weights would change the answer. The reviewer also gives the code a hosting-readiness rating of 3 out of 5: it runs well, but needs about 8 to 9 developer-days of hosting work, including the AWS build, before real data goes in (the reviewer's own figure was 6 to 8; reconciled in 10.5).

# 7. What moving later involves
## 7.1 What is the same for every move
- Custom domain from day one. Lower the DNS time-to-live to 60 seconds two days before the move.
- Logins survive: sessions are database rows, so users stay signed in if the domain is the same.
- The data copy is pg_dump --format=custom and pg_restore between two PostgreSQL 16 servers (the same tools the backup and restore scripts use), or logical replication if a short window matters. The schema uses no database extensions and no host-specific features (HST-13), so it loads unchanged. At today's size a dump and restore takes minutes to under an hour (reviewer's estimate).
- No maintenance mode exists in the code. To freeze writes, stop the API container (or scale the service to zero, or remove the Vercel production alias) and let Meta, WhatsApp and Shopify retry (their retry policies were not verified). Add a "back at HH:MM" 503 page at Caddy for the window.
- Carry these secrets across unchanged: APP_SECRET, BACKUP_ENCRYPTION_KEY, META_*, WHATSAPP_*, SHOPIFY_WEBHOOK_SECRET, BANK_MAIL_*, CRON_SECRET.
- Verify before switching DNS: run npm run integrity against the new database, compare row counts of journal_lines, stock_movements, invoices, files and the trial balance on both sides, send a test webhook, sign in as three roles, upload a file, download an old file.
- Keep the old environment read-only for 14 days, then export a final dump to the Mumbai bucket and delete.
- Files can move between database, disk and S3 gradually: the code looks in both places, so copy first, then flip the new-upload setting FILE_STORE at the switch.
