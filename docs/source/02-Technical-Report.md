# 1. Purpose, scope and how to use this report
## 1.1 Purpose
This is the technical report that the proposal promises: "each finding with where it is, why it matters and how to fix it". It is written for the developer who will do the work. It does four things:
- It says how the review was done and exactly how much of the code was read, so you know what the findings do and do not cover (section 2).
- It gives the 222 fixes as one register, ordered into three waves, each with a level, an effort and a proof (sections 7 and the master register).
- It teaches the patterns behind the findings, so a new screen or route written next month does not repeat them (section 4).
- It tells you what to keep, so that fixing does not break what is sound (section 6).
The fifteen area reports are the line-by-line part of this report. They are bound to it as Annexes A to O (section 8). Nothing in this file replaces them: where this file copies a finding it copies it exactly, and where it summarises it says "summary".
## 1.2 Scope
In scope: everything tracked in the repository at the commit above, which is the API (about 21,300 lines), the web app (about 15,900 lines), the shared package, 43 SQL migrations, the team's tests, and the build, deploy and CI files. Prior audits (AUDIT-REPORT-v2.md, AUDIT-REPORT.md, docs/CODE-REVIEW.md) were used as leads, never as proof: every reviewer read the code and recorded for each earlier item whether it was Confirmed, Changed or Not reproduced.
Not in scope, and quoted separately by the proposal: building the larger fixes, a live penetration test, a load test, and a chartered accountant's sign-off on the tax rules. Where a finding rests on tax or labour law, the register marks it "Needs expert" (CA 21 items, counsel 4, security test 4, labour law 6).
This report describes the unmodified commit. The security fixes that the proposal promises are applied on separate copies of the code and are described in ..\fixes\FIX-A-NOTES.md, FIX-B-NOTES.md and FIX-C-NOTES.md. They are not reflected in the findings below, and the register's "fixed by review branch" field is empty for every item.

## 1.4 Conventions
- Level: Critical (could block go-live or lose all data), Serious (wrong books, GST or pay, or a security exposure), Moderate (will be hit in normal use within the first months), Minor (polish and rare cases), Note (observation, or something checked and found sound).
- Wave: Wave 1 is before any real data goes in (data shape, immutability, secrets, backup and restore, anything that lets one person pay or approve themselves, anything that exposes personal data, and every Critical). Wave 2 is what must be true on go-live day (compliance filings, reconciliation, monitoring, import tools, rate limits, key business-logic defects). Wave 3 is hardening, polish and the larger builds.
- IDs: a source finding has the reviewer's prefix (ARC architecture, DAT data model, ENG core engines, SCA security access, SCB security surface, TST tests, INT integrations, WEB front end, AIX AI features, OPS deployment, LIB libraries, HST hosting, FIN money and compliance, TRD trade, PPL people). An RC number is a master item: it may merge several source findings that share a root cause and a fix. The traceability table at the end of master-register.md maps every one of the 387 source findings to an RC number.
- Effort is developer-days for one competent developer who knows this code, including the tests named, excluding review and accountant time.
- Status words as the reviewers used them: Confirmed by test (a proof test fails today), Confirmed by code read (the lines were read and the behaviour follows from them), To confirm (the finding states the check that would settle it).
- Code excerpts are at most ten lines. Secrets: none appear anywhere in this report or its appendix; the reviewers did not record any.

# 4. Cross-cutting themes
Most of the 222 items are not 222 different mistakes. They are a dozen habits, each repeated in several places, and each is a place where the next feature will go wrong in the same way. Twelve are described below. Each has a plain-words concept, the evidence in this code, and where to start. RC numbers point to master-register.md; the source IDs are in brackets so you can open the reviewer's finding. Where a statement is a summary of the register rather than a quotation, it says so by wording such as "the register says".
## Theme 1. Permission checks sit only at the router, and they check the role, not the record
Concept. Every route calls requirePerm('x:y') at the door, and a few response filters hide cost and phone numbers. That is the whole access model. It answers "may this role use this feature?" but never "may this person see this particular row?", and it lives in the HTTP layer, so any code that calls a service function directly (a background job, a new AI tool, a script) skips every check.
Why it bites. The front end makes it feel safer than it is: menus hide what a role cannot use, but the code itself labels that a hint (apps/web/lib/session.tsx:28). The real gate is the one at the route, and it is only as wide as the role.
Evidence.
- RC-041 (SCA-01, PPL-10, AIX-11): a salesperson cannot download the lead list as a file (the export needs lists:export), but the JSON list route pages 5,000 rows at a time with phone, email and address, and any lead can be edited (leads.ts:339-375, lib/http.ts:168-173 and :263-270).
- RC-171 (AIX-01): requirePerm is in the route files; the Ctx object carries a user but no check (lib/http.ts:20-21); cost hiding is mounted by URL prefix (lib/http.ts:222-231, app.ts:182-183, 210). Anything that calls createPurchaseBill and its neighbours directly bypasses all of it.
- RC-042 (AIX-02) and RC-040 (SCA-15, SCB-14): masking and the "who looked" log cover the detail page but not lists, the phone lookup, exports or the email column.
- RC-164 (SCA-17): cost prices reach Operations through job work, and the masters workbook skips the cost filter.
- RC-151 (WEB-23, TRD-30): some roles can open a screen they cannot complete.
Right way. Put the check where the data is read: a small can(ctx, permission, row) helper in the service layer that routes, jobs and tools all call; scope list queries by owner or entity; and add a registry test that fails when a service function reachable from a route has no check. Start with RC-041, then RC-171 and RC-042 together.
## Theme 2. Safeguards that are opt-in or default to off, so the system fails open
Concept. A safety control must fail closed: if it is not configured, the system should refuse to start or shout, not carry on looking healthy.
Evidence.
- RC-001 (OPS-01): with only the five values the README asks for, the backup writes a plain dump on the same disk as the database and quietly skips the off-site copy (compose.prod.yml:117,122; deploy/backup.sh:26,37). Nothing reports it, and nothing reports a success either.
- RC-017 (OPS-03): the restore drill passes on an empty database (deploy/restore-drill.sh:33,46-52; integrity-cli.ts:20), so "tested monthly" cannot be believed.
- RC-132 (ENG-08, TRD-07, SCA-25, AIX-09, ARC-17, DAT-23): the double-click guard works only if the browser sends an Idempotency-Key; with no header there is no protection (lib/idempotency.ts:23-24), and a repeat is matched on user, method and path only, not on the amount sent (:37-39).
- RC-054 (SCB-01, SCA-14, INT-12): the public enquiry form has a captcha and a strict limit (30 per 10 minutes), but the website-form webhook reaches the same lead capture with a 600-per-minute limiter and no captcha (app.ts:153-159 against :165-170; crm.ts:493-510).
- RC-081 (ARC-12, OPS-31, SCB-21): the server starts with whatever settings it is given; the register says a missing NODE_ENV puts the books in a local file and weak production secrets are accepted (config.ts:26-28, 34, 48, 53, 87, 98-100, 105).
- RC-021 (SCA-22): the first admin can be created locked out when the seed password is blank.
- RC-146 (SCB-06, WEB-24, SCB-19): no browser security headers on any page; token pages can be indexed and cached.
Right way. Make required settings mandatory (a startup check that lists every missing value and exits), make the unsafe choice an explicit opt-out flag such as ALLOW_LOCAL_ONLY_BACKUPS=true, and add a "dead man's switch" so a success announces itself and silence means trouble. Start with RC-001, RC-081 and RC-132.
## Theme 3. "Append-only" and "immutable" are enforced in code but not in the database
Concept. A rule that only the application follows is a habit, not a guarantee; the database is the last line, and it should refuse what the application should never do.
Evidence.
- The database does protect invoices, journals, stock, the audit log and unit history with triggers (drizzle/0001_rules_and_views.sql:11-105, 0027). That is the strength to keep (section 6).
- RC-004 (DAT-04, DAT-11): posted bills, payments, expenses and payslips can be changed or deleted with plain SQL, and deleting a payroll run cascades to its payslips (schema.ts:1562, 1636).
- RC-003 (OPS-04, ENG-22): the app login keeps UPDATE and DELETE on every table (deploy/db-app-user.sh:24-25), and the owner password, a superuser, sits in the API container's environment (compose.prod.yml:38-39), so one environment read can switch the triggers off.
- RC-024 (DAT-10): 119 of 159 numeric columns and 61 of 110 tables have no CHECK, so none of the arithmetic identities is enforced by the database.
- RC-030 and RC-031 (DAT-15, ENG-10, ENG-09, SCA-20, AIX-04): the audit trail depends on about 185 hand-written audit() calls, and 33 of the 230 write routes leave no entry, including every login and almost every export.
- RC-012 (FIN-07, ENG-03, FIN-27): the filed-month lock guards only half the doors, and nothing records what was actually filed.
Right way. Add triggers for the remaining posted-document tables, a separate owner and runtime login that never share a container, CHECK constraints for each identity (for example grand_total = sum of lines), and a trigger-based audit for the tables that matter. Start with RC-003, RC-004 and RC-012 while the tables are empty.
## Theme 4. Hand-rolled parsers and checks on untrusted input
Concept. Parsing text that comes from outside (a bank file, an email header, a URL, a PDF) is a job for a tested library or a strict allow-list, because the hand-written version covers the cases the author thought of and nothing else.
Evidence.
- RC-118 (INT-07, SCB-02): the CSV reader splits on commas without checking the cell count, so an unquoted 9,111.00 becomes Rs 9 (bank-csv.ts:35-67); and one crafted cell makes an amount pattern take quadratic time (30, 108 and 490 ms for 5,000, 10,000 and 20,000 spaces, bank-csv.ts:98), enough to freeze the whole API.
- RC-144 (INT-02, SCB-03): the sender check matches the bank by substring (bank-mail.ts:44-47) and accepts the first dkim=pass found after splitting the header on every ; (mailbox.ts:98-107).
- RC-097 (SCA-21, SCB-12, WEB-09): the post-login next check blocks //evil.com but not /\evil.com (app/login/page.tsx:21-23).
- RC-135 (SCB-15, INT-23): PDF and email parsing run inside the web server's own thread with no time or memory cap (bank-pdf.ts:33-48, mailbox.ts:69-72).
- RC-168 (LIB-09): the shared date check accepts 31 February, so a bad date reaches the database and returns a 500.
- RC-117 (LIB-03, INT-25, WEB-22): the importers cannot read what the sources produce (no Excel, comma-only CSV, UTF-8 only, 1 MB cap).
Right way. Use a vetted parser for each format, validate the result against the totals the file itself carries (the PDF reader already refuses a statement whose running balances do not follow, bank-pdf.ts:195-207), and run untrusted parsing off the web thread with a time cap. Each finding names its own better option. Start with RC-118 and RC-144.
## Theme 5. Check once, then trust; read today's rule instead of the one that applied
Concept. A business fact (a credit limit, a salary, who issued an invoice, what was filed) can change after the event. Either record the value at the time (a snapshot), or re-check at every step. Reading the current master later gives a different answer from the one that was true on the day.
Evidence.
- RC-061 (TRD-02, TRD-18): the dealer's credit limit and overdue bills are checked once, at order confirmation (sales.ts:302); delivery and invoice never re-check.
- RC-013 (PPL-03, PPL-06): reopening or approving a past month re-reads today's rules, PF flags, professional tax, leave policy and bank account for everything except the salary figure (payroll.ts:79-126); reopening also books the reversal into today's month.
- RC-022 (DAT-09): an issued invoice freezes the buyer but not the seller, so old invoices reprint with today's company name, GSTIN, address and bank (schema.ts:735-790).
- RC-012 (FIN-07): "Mark filed" stores no snapshot of the figures that were filed.
- RC-098 (PPL-15, PPL-18), RC-111 (FIN-14, TRD-09, ENG-21), RC-163 (ENG-17, ENG-19): back-dated salary changes, unbounded document dates and in-flight postings that a lock move does not wait for.
Right way. Snapshot at the moment of issue or approval (seller fields on the invoice, rule values on the payslip, figures on the filing), and re-check at each step that can change the exposure. Start with RC-022, RC-012 and RC-013 while no invoice exists.
## Theme 6. One person can do everything: no second pair of eyes
Concept. Maker-checker means two different people for the two halves of a risky action, and the checker must approve exactly what the maker produced (identified by a version or hash), not "the current state". A control of the form "A cannot touch A's own X" is only as strong as the link between A and X.
Evidence.
- RC-034 (SCA-05, PPL-01, PPL-02): an admin can unlink their own employee record and then set their own pay (hr.ts:846-849), and anyone with payroll:manage can pay themselves a cash advance with no "not yourself" check (payroll.ts:319-341).
- RC-035 (SCA-06, PPL-07): one payroll user can prepare, adjust, approve and pay a month, and approveRun recalculates before approving (payroll.ts:145-150, 417-432).
- RC-036 (PPL-04): a change of someone's bank account is not in the audit trail and needs no second person.
- RC-037 (SCA-11, TRD-05, TRD-24) and RC-038 (FIN-09, ENG-02, ENG-15): adjustments, purchase orders, price lists, service bills, payments out and the opening-stock import can be made and approved by the same person.
- RC-039 (SCA-12, FIN-12): closed-year reopening needs two people, but one admin can create the second, and the lock does not follow the approval.
- RC-055 (SCA-02) and RC-089 (SCA-04): no second factor and no per-account lockout on accounts that move money.
Right way. One small approvals table (requester, approver, version hash) used for payroll, bank-account changes, stock adjustments and role changes, plus a rule that the approver was not created by the requester. The people reviewer prices a reusable approvals table at about 2 days on top of the guards (PPL-01). Start with RC-034, RC-035 and RC-036.
## Theme 7. Silent failure: no retry, no alarm, quiet truncation
Concept. A system that fails loudly can be fixed the same day; one that fails silently loses leads and money for weeks. Every background step needs a retry, a limit on how long it can run, and a signal when it succeeds or stops.
Evidence.
- RC-084 (INT-01, INT-15): a webhook event that fails is never retried or reported, so an expired Meta token silently loses leads (crm.ts:188-228; core/jobs.ts:25-53 has no retry job).
- RC-083 (OPS-07, OPS-06, ARC-18): nobody outside the server watches the server; the health check says ok without touching the database.
- RC-082 (ARC-08, AIX-06, LIB-07, ENG-24, OPS-25, HST-07): the job loop has no queue, retry, timeout, watchdog or overlap guard, and on Vercel it runs once a day.
- RC-086 (ARC-05, WEB-03, WEB-04, WEB-05): lists, pickers and exports stop at a fixed size and "Show more" fails; the export stops at 5,000 rows without saying so.
- RC-137 (INT-17), RC-142 (INT-28), RC-184 (INT-14), RC-158 (LIB-08, OPS-29): statement mail intake loses files on a database error; a repeat enquiry makes no sound; a WhatsApp timeout says "nothing was sent" when it may have been; error tracking is home-made and blind to the browser.
Right way. A Postgres-backed job queue (the architecture reviewer recommends pg-boss, finding ARC-08), a heartbeat to an external monitor after every successful run, an alert for every "failed" state, and an explicit "list is cut short" signal on every list. Start with RC-083 and RC-084.
## Theme 8. Tests that mirror the code
Concept. A test is only worth having if it can fail when the code is wrong. A test that reads the code to build its expectation, or builds its input to match what the code accepts, passes whatever the code does.
Evidence.
- RC-153 (TST-07): the permission sweep reads each route and its requirePerm from the source with a regular expression (robustness.test.ts:21-43); delete the check from a route and the sweep skips it; the admin role is skipped (:78).
- RC-063 (ENG-25, TRD-23, TST-04): expectBooksHealthy, called 55 times (test/helpers.ts:124-136), reduces to "debits equal credits" plus one stock total, so it stays green while stock and value leak.
- RC-143 (INT-20, TST-09): integration tests use hand-made payloads and awaitProcessing: true, never the production path (helpers.ts:67-74).
- RC-069 (TST-05, TST-06, TST-15): a desk-check mutation analysis of the 25 most critical functions says the suite would stop 13, about 52 percent; the survivors are paise rounding, "exactly at the limit" cases and locks.
- RC-154, RC-155, RC-157 (TST-10, TST-11, TST-17): the default engine is PostgreSQL 17 in memory with one connection; rate limiters are off and passwords hash with 4 rounds under test; no test makes a save fail halfway.
- RC-005 (TST-01, TST-16): the real-PostgreSQL CI job, the only place the lock and numbering tests run on the engine the live server uses, failed before any test ran in 4 of the last 8 runs, including the last two (checked on the public GitHub API on 28 October 2026).
Right way. Test against an independent oracle (a hand-worked figure, a second report computed differently), pin the permission matrix as data, and run the same suite on a real PostgreSQL in CI. Start with RC-005, then RC-063 and RC-153.
## Theme 9. Personal data is copied into places that outlive its purpose
Concept. Every copy of a phone number, PAN or bank account is something that has to be protected, listed and eventually erased. The system copies personal data into logs, chat alerts, audit rows, cached answers and bearer links.
Evidence.
- RC-007 (ARC-11, SCB-04, OPS-08, AIX-07): a failed database query puts names, phone numbers, PAN and bank details, and link tokens into the error log, the console and out to Slack, Google Chat, Discord or ntfy.sh (app.ts:123-128, core/alerts.ts:44-57, lib/errors.ts:138-139).
- RC-011 (DAT-16, SCB-05, PPL-26, INT-19): there is no way to erase, anonymise or time-limit personal data, and the append-only audit log and event tables keep full copies (a phone number is found in audit_log.after).
- RC-132: the idempotency store keeps whole answers, including link tokens, for a day (lib/idempotency.ts:55-61).
- RC-047 (DAT-18, SCB-16): public link tokens are stored in plain text and copied into other tables.
- RC-043 (PPL-23, WEB-37): salary and full bank account numbers are listed for every employee at once and stored as plain text.
- RC-048 (SCB-07, SCA-13, TRD-28) and RC-049 (PPL-16, SCB-08): invoice and estimate links never expire, cannot be switched off and can be made by anyone who can read invoices; payslip links show salary, deductions and IFSC to anyone with the link and cannot be revoked.
Right way. Scrub at the edge of every outbound path (log, alert, cache), store token hashes, give every table that holds personal data a retention rule and an erase path (the audit log needs a redaction design, because it is append-only), and give every bearer link an expiry and a revoke. Start with RC-007, then RC-011 and RC-049.
## Theme 10. State held in one process's memory
Concept. Anything kept in a variable (a rate-limit counter, a permission cache, a timer) disappears on restart and is not shared by a second copy of the server.
Evidence.
- RC-088 (LIB-05, HST-05, SCB-09) and RC-089 (SCA-04, ARC-22): rate limits count in memory, so they reset on restart and are not shared; password guessing is limited per address only.
- RC-095 (ENG-16, SCA-16, AIX-14, HST-11): the permission matrix is cached per process (core/settings.ts:119-127, constants.ts:403-415); a revoked permission stays granted on a second server copy.
- RC-082: the job loop lives inside the API process.
- RC-015 (ARC-16, HST-10) and RC-191 (HST-03): the code is written for a long-running server and loses limits, jobs and uploads on Vercel.
Right way. Put counters, caches and job state in Postgres (or a shared store) from the start, even on a single server, so a second copy or a restart changes nothing. Start with RC-015 (decide the host) and RC-095.
## Theme 11. The common path is right; the statutory edges are simplified
Concept. The core flows were worked out by hand and match the figures. The rules around them (credit eligibility, reverse charge, TDS, PF, ESIC, professional tax, e-invoice) were built for the usual case, and the unusual case is a wrong return.
Evidence.
- RC-014 (FIN-02, FIN-03, TRD-04): input credit is claimed on bills from suppliers with no GSTIN, from composition dealers and from foreign suppliers whose state flag is blank.
- RC-057 (FIN-05): no reverse charge anywhere (purchasing.ts:56-62 says so in a comment).
- RC-060 (FIN-08) and RC-169 (PPL-05): TDS is typed in by hand, for suppliers and for salary (packages/shared/src/payroll.ts:59-60).
- RC-104 (PPL-08) and RC-102 (PPL-11): PF and ESIC are worked from a made-up "Basic = 50% of gross"; professional tax is a flat number per person.
- RC-059 (FIN-06, FIN-28) and RC-170 (FIN-01): the GSTR-1 file has never been checked against the portal's rules, and e-invoice and e-way bill are typed-in references.
- RC-008 (DAT-01), RC-009 (DAT-02), RC-010 (DAT-03): rates are limited to two decimals, foreign amounts are re-derived by division, and a second legal entity is half-built. The proposal says multi-company, multi-currency, payroll and TDS were out of v1; all four were built and several serious gaps sit in them.
Right way. Treat each statutory rule as a table-driven module with its own tests worked from the source text, and have the chartered accountant sign off the rules before a return is filed from it. 21 register items need a CA. Start with RC-014 and RC-059.
## Theme 12. One thread, one transaction, no time limit
Concept. A single slow request on a single thread, inside an open transaction with no time limit, can stop everyone.
Evidence.
- RC-080 (ARC-06, ENG-13, OPS-16): no lock, statement or connection timeouts; the pool is new pg.Pool({ connectionString, max }) with nothing else (db/client.ts:27).
- RC-087 (ARC-10): bank auto-matching is quadratic, runs on the web thread inside an open transaction, and is called on every import including the 15-minute mailbox job (bank.ts:110-129, 204).
- RC-135, RC-118: PDF, email and CSV parsing on the web thread (Theme 4).
- RC-176 (ARC-01 to ARC-04): lists and reports add up a whole ledger before they keep 100 rows, so 8 of the 15 heaviest screens take 1 to 12 seconds at 50,000 rows (measured on PGlite; an upper bound).
- RC-053 (ENG-11, ENG-12, TST-03): item locks block unrelated inserts and two lock-order inversions can deadlock.
- RC-078, RC-079 (ARC-07, OPS-15, ARC-13, OPS-17): a database restart can end the process, and stopping the API cuts requests short.
Right way. Set statement_timeout, lock_timeout and idle_in_transaction_session_timeout, a pool wait limit, move heavy parsing and matching into queued jobs, and keep report queries to the rows they return. Start with RC-080.
# 5. The 25 findings that matter most
## How these 25 were chosen and how to read an entry
These are 25 master items (RC numbers). The choice is a judgement, made on four tests, applied in this order: (1) every Critical; (2) loss or exposure that cannot be undone once real data exists (backups, immutability, personal data, anything an outsider can reach); (3) wrong books, GST or pay; (4) every row of the proposal's headline-risk table has at least one entry, so the owner can see each promise tested. They are listed in the order a developer should meet them: the Critical, then Wave 1, then Wave 2.
The 25 are not the only urgent items. Wave 1 holds 49 items; the others are in the register. Important items deliberately not repeated here: RC-011 (no erase or time limit for personal data), RC-018 ("data stays in India" is true on paper only), RC-039 (closed years and the period lock), RC-170 (e-invoice and e-way bill, a 12-day build in Wave 3), RC-061 (credit limit checked once), RC-085 (Shopify edits and refunds dropped) and RC-169 (salary TDS).
Each entry has the same shape:
- A header with the RC id, level, wave, effort, confirmation, the proposal row it answers, and a link to its block in master-register.md.
- The source findings merged into it, with the Annex and the path and line of each in the area reports.
- A faithful copy of the primary finding from its area report, below a line saying which Annex and ID it comes from. The primary finding is the one with the highest level among the sources (the first listed if tied; for RC-012 the main finance finding, FIN-07). The copy has the reviewer's template in full: where, code (at most ten lines), what happens, why it matters, concept, fix, better option, effort, proof, status, related. It is not edited.
- For items that merge more than one finding, a short list of the other findings (title and location only) and the register's merged fix and proof. These two parts are the register author's summary of the sources, and are labelled "summary".
The primary finding's effort is for that finding alone; the item's effort in the header is the merged figure and is the one to plan with.

OPS-05 [Serious] Ransomware or a stolen server can read, and possibly overwrite, every backup: the keys sit beside them
- Where: compose.prod.yml:116-123, deploy/backup.sh:27,38,63, deploy/restore-drill.sh:28,30, README.md:89-90
- What happens: the AES key and the S3 access key are both in .env.production on the host that holds the data. - What happens: the only recovery point is a once-a-day pg_dump. Copied from Annex M, finding FIN-10 (the reviewer's text, unchanged below the heading):
FIN-10 [Serious] Unpaid bills are not brought in one by one, so old invoices cannot be returned, credited or chased
- Where: apps/api/src/modules/opening.ts:36-40 and 208-229 (one balance per party), apps/api/src/modules/sales.ts:735-737 (a credit note needs an issued RadCore invoice), apps/api/src/modules/collect.ts:23-39 (reminders read v_invoice_outstanding only), apps/api/src/modules/payments.ts:63-80.
- Code: n/a (the design choice is stated in the file header: "Old bills are not brought in one by one: a party's balance is one figure").
- What happens: A dealer owes Rs 45,000 over three Vyapar invoices. RadCore holds "Dr Debtors 45,000" on the party. (a) When the dealer returns goods bought on one of those invoices there is no RadCore invoice to credit, so there is no GST credit note in the books; the only route is a manual journal, which leaves GSTR-1 wrong. (b) Receipts against that balance sit "on account"; the reminder list and the overdue chase (whoOwes) do not see the Rs 45,000 at all (v2 reports a Rs 50,000 opening receivable missing from reminders; I confirm from the query that only invoices appear). The ageing report now shows it as "not on a bill" (accounting.ts:703), which fixes the ageing but not the chase. (c) Supplier bills: no way to settle a particular pre-cut-over bill, and the 180-day rule (credit is reversed if a supplier is not paid within 180 days, Rule 37, to be confirmed) cannot be tracked on bills RadCore never saw. (d) Cross-area: the vehicles sold before cut-over have no units row, so a warranty job card for them cannot be created.
- Why it matters to Radboards: Returns and warranty claims on last year's sales are everyday events for a vehicle dealer. Handling them off the books is exactly the kind of leak the move to RadCore was meant to stop.
- Concept: An opening balance is a summary; a receivable is a set of documents. If later events (returns, discounts, disputes, credit notes) refer to a document, the document must exist.
- Fix: Add a fourth import "open documents" (design in Appendix B): unpaid sales invoices and unpaid purchase bills, each with number, date, due date, party, place of supply, amount outstanding, and one summary line (HSN, rate, taxable value) so a credit note can pro-rate. Store them as invoices/purchase_bills with origin = 'vyapar_opening' and gst_reported = true so GSTR-1/3B skip them, post the party balance once as today, and let payments and credit notes allocate to them. Also import sold vehicles' serial numbers (a sold_before_cutover unit status) for warranty.
- Better option: None.
- Effort: 6 developer-days (L).
- Proof it is fixed: import one old invoice of Rs 5,900 (Rs 5,000 + 18%); raise a credit note for half; the party balance falls by Rs 2,950, GSTR-1 for the current month shows the credit note in CDNR with the old invoice number and date, and the import itself adds nothing to GSTR-1.
- Status: Confirmed by code read.
- Related: v2 E-25, F-12, CR-21; proposal "Moving off Vyapar".

# 9. Verification: re-running the proof tests
## 9.1 What the proof tests are
Before this review, an earlier runtime audit (AUDIT-REPORT-v2.md) wrote 338 proof tests for this exact commit. They are in radcore-repo\apps\api\test\audit\ (six files, untracked in git). Each test asserts the correct behaviour. So a test that fails today is a defect confirmed at runtime, and a test that passes today is a fix or a control confirmed. After you fix an item, its test must turn from fail to pass, and the tests that pass today must keep passing. Most items also name their own proof in the register ("Proof it is fixed"), and every Annex section 9 maps each of its findings to a check.
## 9.2 How to run them
From the repository root:
cd apps/api
npx vitest run test/audit --no-file-parallelism
Run one file at a time, or one test by name with -t, as the reviewers did (the full folder is slow and loads the machine):
npx vitest run test/audit/infra.audit.test.ts --no-file-parallelism -t "I-01"
npx vitest run test/audit/auth.audit.test.ts --no-file-parallelism -t "AUTH-L2|A-04"
The default engine is PGlite (PostgreSQL 17 in memory, one connection). To run against a real PostgreSQL 16, set TEST_DATABASE_URL; the harness then creates a throwaway database per file (test/helpers.ts:30-50). Two practical notes from the reviewers: the PGlite worker can crash natively partway through a long file (exit code 3221226505, which is 0xC0000409); re-run that file alone (people.audit.test.ts is the usual one). And one reviewer's 560-second limit cut the 55-test accounting.audit.test.ts off after 25 tests, so allow several minutes per file.

What pass and fail mean, in one line each.
- Fail today means the defect is present at this commit. It is a confirmed finding, not an opinion. Do not "fix" the test.
- Pass today means the behaviour is already right: either a control to protect (section 6) or a proposal claim that is already fixed (proposal-vs-reality.md). If it turns red during your work, you have broken something that worked.
- Skipped (4 tests): three in db.audit.test.ts on PGlite (they run on a real PostgreSQL 16) and one in people.audit.test.ts; the earlier audit does not say why the latter is skipped.
- A fix is done when the named test goes green, the full team suite is still green, npm run typecheck is clean, and the register's "Proof it is fixed" for the item has been run.
## 9.4 Two cautions
- Do not commit the audit folder as it stands. Its 229 failing tests would turn npm test and CI red because the default Vitest pattern picks them up (RC-019, 0.5 day). Wrap each defect test in it.fails, or move the folder to a separate Vitest project run by npm run test:audit in a non-blocking CI job, and remove the marker as each defect is fixed.
- The team's own suite is not a substitute for the proofs. It has about 520 active tests (31 shared and 490 API, of which 8 need a real PostgreSQL), most checked against hand-worked figures, but a desk-check mutation analysis says it would stop only 13 of 25 deliberately broken money functions (RC-069), and the real-PostgreSQL job that runs the lock tests failed to start in 4 of the last 8 CI runs (RC-005). Fix RC-005 first, so every later fix is checked on the engine the live server uses.
# 10. Known limits and assumptions
## 10.1 About this report
- It is compiled, not re-derived. It was written from the fifteen area reports, the master register and the proposal-versus-reality document. The compiler did not re-read the source code; every statement about code is a reviewer's, with the reviewer's path and line. Where this report copies, it copies exactly (section 5); everything else says "summary".
- Coverage figures rest on the reviewers' own coverage tables. The percentages in section 2 count a file as read in full when a reviewer wrote "Fully read" for it. They were worked out by script from the reports and corrected by hand where a status word and its detail disagreed, but nobody re-read the files to audit the claim.
- The merge into 222 items is a judgement. Findings were joined when they shared a root cause and a fix, and kept apart when they shared a file but needed different fixes. The level of an item is the highest among its sources, and its confirmation is the weakest. The traceability table lets you undo any merge.
- The top 25 is a judgement (section 5). It does not replace the register.
- The register was amended on 29 October 2026 (for example RC-191, moved by the hosting decision, see the note in section 7). If master-register.md and master-register.json ever disagree, the JSON is the machine-readable copy and the one check-register.cjs tests.
## 10.2 Limits of the evidence
- Reading, not running. Almost all findings are "Confirmed by code read": the lines were read and the behaviour follows from them. 28 items are "Confirmed by test" (a proof test fails) and 20 are "To confirm", each with the check that would settle it. Nothing was run on a live host or against a real outside system (section 2.5).
- Measured numbers are upper bounds. The 50,000-row timings are PGlite (PostgreSQL compiled to WebAssembly, single thread) on a shared laptop. The reviewer assumes, without measuring, that a real PostgreSQL 16 on a dedicated 2-vCPU server is 2 to 5 times faster. The before and after ratios are the reliable part.
- Dates and versions. Library versions, licences, advisory counts, prices and vendor behaviour are as of 28 October 2026 and will move. Where a reviewer could not check one, the finding says so and gives no number.
- Statutory and legal points are not legal or tax advice. GST, TDS, PF, ESIC, professional tax, the DPDP Act 2023 and labour law were taken from secondary sources reachable on 28 October 2026. Register items marked "Needs expert" (CA 21, counsel 4, security test 4, labour law 6) must be confirmed by the chartered accountant, counsel, a labour adviser or a live security test before they drive a build or a filing.
- The PRD of 7 October 2026 is not in the repository. The proposal's "promised versus today" table stands in for it.
## 10.3 Assumptions the reviewers made (merged)
- Production is the documented Docker Compose stack: Caddy in front, one API container, one web container, PostgreSQL 16 in India. Where the team chooses Vercel instead, several findings get worse (in-memory rate limits, the 15-minute job loop that becomes a daily cron, the 4 MB upload cap) and Annexes A, E and L say which.
