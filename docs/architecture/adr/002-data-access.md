# ADR-002: Drizzle ORM and data access

- Status: accepted
- Date: 2026-11-05, revised 2026-11-06 after two rounds of the auditor's review
- Ticket: RAD-8 (M0-03). Covers RC-221.
- Decided by: N1 (Sarthak, 5 Nov 2026: Drizzle ORM). The coordinator accepted the SQL zone in §3 on 5 Nov.
- Builds on: [ADR-001](001-layers.md) (package layout, table ownership, the module transaction, the E-rules). Pairs
  with ADR-005 (database conventions: CHECKs, triggers and views).

## Context

v1 used Drizzle for its schema, but its list and report routes carried their SQL inline (v1
`docs/ARCHITECTURE.md` §12, "SQL in routes"). Nothing stopped a new SQL string or a `dangerouslySetInnerHTML`, and
the Meta lead pull followed whatever "next page" URL the response contained without checking its host (RC-221).
The senior reviewer's main point about v1 was that application code should not hold SQL.

## Decision

### 1. Queries go through Drizzle, never through strings

Application code reads and writes the database in exactly two ways, always through its module transaction
(`salesTx(ctx)` and so on; §4, ADR-001 §5):

- **Drizzle's relational queries** (`query.<table>.findMany / findFirst` with `columns`, `with`, `where`,
  `orderBy`, `limit`) for reads that follow relations.
- **Drizzle's typed query builder** (`select / insert / update / delete`, with the comparison and aggregate helpers
  on the allowlist in L1) for everything else.

No SQL text appears in a library, the API, the worker or the web app. That includes the `sql` that Drizzle 0.45
hands to relational `where` and `orderBy` callbacks, which the module transaction removes (§4). Drizzle version:
the 0.45 line (ADR-003). The examples below use 0.45's API.

**Two layers keep it that way.**
- **The runtime is the real guard.** The module transaction is a runtime object that offers no raw route (§4), and
  the database refuses what the runtime login may not do (ADR-005 §7).
- **Lint is the early warning** that names the mistake in review.

Where the two overlap, the runtime decides.

### 2. Repositories in packages/db

Each module has its repository files in `packages/db/src/<module>/repo.ts`, next to its tables (`tables.ts`) and
relations (`relations.ts`). A repository is a plain function `(tx, scope, args) => result` built only from the
relational API and the query builder. `tx` is that module's transaction object.

- Libraries call repositories, or Drizzle directly for a one-off query on their own tables. A query that two
  services need goes into the repository, so it isn't written twice.
- A repository may join other modules' tables to read them. It writes only its own module's tables: the module
  transaction's `insert`, `update` and `delete` accept only that module's tables, by type and at run time (§4).
- A read that returns a person's records takes the **scope** as its own argument, and ANDs it into `where`
  (worked examples below). Scope is never folded into the caller's filter.
- `scopeWhere` **fails closed**. Its column mapping is typed so every scope kind needs its column, and a missing
  one throws. It never uses `notInArray`.
- Repositories return numeric columns as Drizzle gives them (strings). lib-common turns them into decimals
  (ADR-005). ADR-001's E4 (no `any`, casts or reflection) applies to `repo.ts` files too.

### 3. The SQL zone

SQL is written only in the SQL zone, which is inside `packages/db` and reviewed like code:

| Where | What | Why it must be SQL |
|---|---|---|
| `packages/db/migrations/**` | migrations generated by drizzle-kit from the schema, plus hand-written ones (`drizzle-kit generate --custom`) for triggers, functions, the partitioned logs and pg-boss's own schema | none of these has a Drizzle declaration |
| `packages/db/views/<name>.ts` (one view per file; not `index.ts`) | `pgView(...).as(...)`. The query builder is used where it can express the view, `sql` where it can't (window functions, recursive CTEs). drizzle-kit generates the `CREATE VIEW` migration. | reports over ledgers (ADR-005) |
| `packages/db/src/*/tables.ts`, `packages/db/src/columns.ts` | CHECK constraints, generated columns and DB-side default expressions in table declarations: DDL only, never run as a query | Drizzle declares CHECKs with `sql`. Keeping them in the schema means drizzle-kit generates them, so schema and migration can't drift apart. |
| `packages/db/src/request-context.ts` | the one helper run at the start of each transaction. It sets the acting principal and request id for the audit triggers, and the contract's statement timeout (`set_config(..., true)`), with values passed as bound parameters, never pasted into the text. The triggers read the principal with `nullif(current_setting('app.principal', true), '')` and raise if it is missing (ADR-005, M1-12). | a session setting has no query-builder form |

**Where `sql` may appear, by position (L1).** Inside the zone, a `sql` template may appear only:
- as the argument of `check()`, `.default()`, `.generatedAlwaysAs()` or `pgView(...).as()`;
- inside the body of the request-context helper.

It may not appear anywhere else, even in a zone file. So no zone file can export an SQL value of its own for a
repository to reuse.

**No query-time SQL in the schema.** The schema declares no `$defaultFn`, `$onUpdate`, `$onUpdateFn` or
`customType`. Defaults are database-side (`.default(...)`), and the audit columns are filled by triggers
(ADR-005 §5). So "DDL only" holds.

The zone adds the schema files and one helper to the ticket's "migrations and views", because Drizzle declares
CHECKs in the schema with `sql`. Moving them into hand-written migrations would make two lists to keep in step.

**Applied migrations never change.** A change is a new migration (M1-07 runs them forward only). CI (M0-08) fails
when a migration file that exists on `dev` is edited, renamed or deleted, or when `migrations/meta/_journal.json`
changes other than by appending an entry with a later timestamp. Drizzle's migrator compares timestamps, not hashes,
so CI is what notices an edit.

**The runtime login isn't the owner** (M1-06). Even SQL that slipped through couldn't alter a table or switch off
an audit trigger.

### 4. Transactions and the module transaction

**Who opens it.** The generic handler and the job runner open the transaction (ADR-001 §6). Nothing else does.
lib-platform exports the opener only from its `runtime` entry, which only `apps/api` and `apps/worker` may import
(L7).

**The contract declares it.** `defineContract` and the job contract take a required
`tx: { readOnly, isolation, statementTimeoutMs? }`:

- `method: 'GET'` forces `readOnly: true` by type, so a cross-site GET can't write.
- `isolation: 'repeatable read'` is allowed only with `readOnly: true`. A report that combines several queries
  uses it, so all its parts see one snapshot (the books check, M2-07).
- A write is `{ readOnly: false, isolation: 'read committed' }`. Saved-once applies to every `readOnly: false`
  contract (ADR-001 §6).
- `statementTimeoutMs`, when present, is a positive integer up to a configured maximum. `0`, which would switch the
  timeout off, is refused (RC-080).

**Timeouts.**
- lib-platform's pool sets `statement_timeout`, `lock_timeout` and `idle_in_transaction_session_timeout` on every
  connection (node-postgres 8.23 supports all three), plus a pool wait limit. Values come from config (M1-10).
- A contract's `statementTimeoutMs` is applied by `request-context.ts` for that transaction only. RC-080 is
  designed out here and proved in M1-08.
- Connections go straight from the pool to PostgreSQL, or through a pooler in session mode. A transaction-mode
  pooler would drop the startup settings, so it isn't used (ADR-004).

**Paging.** List contracts cap `limit` (200 at most) in lib-common's base paging schema (RC-176, M1-29).

**The module transaction is a runtime object, not a type alias** (built in `@radcore/db/<module>`, M1-08). It
wraps the request's Drizzle transaction and exposes only:

| Member | What it allows |
|---|---|
| `query.<own tables>` | relational reads. Its `where` and `orderBy` callbacks receive operator objects with `sql` removed, both in the type and in the object passed at run time |
| `select()` | the query builder, reading own tables, relations and views. It isn't checked at run time: what it can read is limited by D7, since only the owning library can import a table |
| `insert`, `update`, `delete` | **own tables only**, checked by type and at run time against the module's table set |
| `transaction(cb)` | a savepoint. `cb` receives a **new module object of the same module**, with its own handle that ends with the savepoint, never Drizzle's raw `PgTransaction` |

- It has no `execute`, no `_`, no `$with` and no driver handle. Those members don't exist on the object, so a cast
  can't reach them. Every builder it hands out, and every builder those return, has no `session` and no `_`
  members, no `config` and no `dialect` either, and refuses to be changed (set, define, delete), so a cast can't
  reach the pool's client through one or clear a `where` a guard has checked.
- **It works only while its transaction does.** The module object and its builders look the transaction up each time
  they run, so one kept past commit or rollback (a `forEach(async ...)` is enough) throws instead of running on a
  client already back in the pool. A savepoint's object ends with the savepoint.
- `query.<key>` checks that the client's table under that key is the module's own, so two modules using one key
  can't read each other's table.
- **Writes are always bounded.** The wrapper also wraps the builders that `update(...).set(...)` and `delete(...)`
  return:
  - `.where(cond)` throws `UnboundedWriteError` when `cond` is `undefined`, which is what `and(undefined, ...)`
    returns when every optional filter is empty;
  - running an update or delete with no `.where()` also throws, whichever member runs it: `then`, `catch`,
    `finally`, `execute`, `prepare` or `_prepare`.
- **No empty exclusion.** Drizzle 0.45.4's `notInArray(col, [])` returns `sql\`true\`` (`conditions.ts:327`), which
  would make a whole-table write. `notInArray` is not on L1's allowlist. Code uses `notInNonEmpty(col, list)` from
  `packages/db`, which throws on an empty list.
- Unit tests (M1-08):
  - an all-empty filter on update and delete throws;
  - `notInNonEmpty(col, [])` throws;
  - a foreign table passed to `insert` throws;
  - inside `transaction(cb)` the same guards hold;
  - the callback operators have no `sql`.

**Exports.** An export that may be large runs as a job in one `{ readOnly: true, isolation: 'repeatable read' }`
transaction, with its own `statementTimeoutMs` and a row cap.
- It writes the file to a local temporary file while the transaction is open, and uploads it to the file store
  **after commit**. There is no network call inside the transaction (ADR-001 §8).
- One snapshot means rows written during the export can't be skipped or repeated, and no transaction waits on a slow
  client.

**Queuing a job: the outbox (M1-26).**
- `ctx.jobs.send` inserts a row into lib-platform's `jobs_outbox` table, in the caller's transaction, with the
  query builder. A save that rolls back leaves no row.
- The relay runs in lib-platform's runtime entry, inside the worker. In one transaction it:
  - selects due rows with `.for('update', { skipLocked: true })`, so two workers never take the same row;
  - sends each to pg-boss with pg-boss's job `id` set to the row's id;
  - deletes the rows.

  A crash between the send and the delete re-sends the row, and pg-boss refuses the duplicate id.
- There is **no ordering guarantee**. Every job handler is idempotent, keyed on what it acts on: the delivery id, the
  document id, or the provider's idempotency key.
- pg-boss is built in `packages/lib-platform/src/db/client.ts` (the L4 file) with `migrate: false`. Its schema is
  created by a hand-written migration run as the owner, from pg-boss's own construction plan. So the runtime login
  needs no DDL. Its pool is counted in the connection budget (ADR-004).

A nested `transaction(...)` (a savepoint) is allowed only where a partial rollback is intended, with a comment
saying why.

## Lint rules (for M0-07 to add, M0-08 to run in CI)

"Server code" means `packages/**`, `apps/api/**` and `apps/worker/**`.

**Each rule is its own rule in a local ESLint plugin** (`radcore/no-sql`, `radcore/no-query-strings`, and so on),
like ADR-001's E-rules. None is an entry in a shared `no-restricted-syntax`, `no-restricted-imports` or
`no-restricted-globals`: in flat config, a later block's options for a core rule replace an earlier block's.
`linterOptions.noInlineConfig: true` means no comment can switch a rule off, and ADR-001's E5 bans `@ts-*`
comments.

**The config is tested (M0-07).** The test calls ESLint's `calculateConfigForFile` on sample files: a `repo.ts`, a
`lib-*` service, a route file, `views/index.ts`, a `views/<name>.ts`, `request-context.ts` and a test file. For
each, it asserts which local rules are on at `error`, with their full selector and pattern sets. It also fails when a
zone list differs from the table below. Widening a zone means amending this ADR in a reviewed PR.

**Each rule's zone is the exact files where it is off, and nowhere else:**

### The outbound client (L8)

All outside HTTP from server code goes through one client, `createOutbound({ name, allowedOrigins, credential })`
in `packages/lib-platform/src/http/outbound.ts`. lib-integrations and the alert sender both use it.

- **Origins.** Each client is created with the exact origins it may reach, for example Meta:
  `allowedOrigins: ['https://graph.facebook.com']`. An origin taken from settings, such as a Shopify shop, is
  checked against a fixed pattern when it is configured (`^[a-z0-9-]+\.myshopify\.com$`).
- **Every request is checked before it's sent**, including a URL taken from a response (Meta's `paging.next`,
  Shopify's `Link` header):
  - the URL is parsed with the WHATWG `URL` class;
  - it must be `https:`, on the default port, with no username or password;
  - its origin must be in the list exactly, with no suffix or substring match;
  - the request is sent to the parsed `url.href`.
- **Credentials.** The client's credential goes in the `Authorization` header, never in the URL (M1-24). Before a
  response URL is used, any credential parameter the client names (for Meta, `access_token`, which Graph API
  paging links do carry) is removed from it.
- **Logs** show only the origin and path, never the query or headers.
  - A client whose URL itself comes from a secret (an alert webhook, a heartbeat address) is created with
    `logPath: false` and logs the origin alone.
  - No refusal message includes the URL.
- **Redirects** are followed by hand (`redirect: 'manual'`), at most 3 hops.
  - Each `Location` is resolved with `new URL(location, current)` and passes the same check.
  - If a redirect crosses to another allowed origin, `Authorization` is dropped.
- **Addresses.** Only global unicast addresses are allowed.
  - The check runs in the connection's DNS lookup hook, on every hop, so the address checked is the address
    connected to.
  - IPv4-mapped (`::ffff:0:0/96`), NAT64 (`64:ff9b::/96`) and 6to4 (`2002::/16`) addresses are unwrapped first.
  - Refused: `0.0.0.0/8`, 10/8, `100.64/10` (including `100.100.100.200`), 127/8, 169.254/16, 172.16/12,
    192.168/16, `::`, `::1`, `fc00::/7`, `fe80::/10`, and all multicast.
  - Environment proxy settings are ignored.
- **Limits.** Each request has a timeout (10 s by default) and a response-size limit (10 MB by default).
- **Proof**, a unit test with a mocked transport, in the ticket that builds the client and again in the Meta
  lead-pull ticket. Allowed:
  - `https://graph.facebook.com/v21.0/123/leads?after=X&access_token=T` is sent once, to a URL without
    `access_token`, with the token in the header.

  Refused, with the transport mock called **zero** times:
  - `https://graph.facebook.com.evil.example/`
  - `http://graph.facebook.com/`
  - `https://user:pass@graph.facebook.com/`
  - `https://graph.facebook.com:8443/`
  - a host resolving to `127.0.0.1`, `0.0.0.0` or `::ffff:127.0.0.1`

  A `302` from an allowed page to `https://evil.example/` makes exactly one transport call (the first hop) and is
  then refused. A redirect chain of 4 hops is refused at the 4th.

## Worked examples

Names such as `ctx.can.scope` and `scopeWhere` are illustrative; the M1 tickets fix the exact APIs. What the
examples fix is the shape:
- no SQL string;
- the module transaction;
- scope as its own argument;
- the relation read;
- keyset paging.

### A list with filter, scope and paging (no SQL string)

Invoices for one screen, filtered by party, status and dates, newest first, with keyset paging. Each page is one
indexed range read, never a count of the whole ledger (RC-176).

```ts
// packages/db/src/sales/repo.ts
import type { SalesTx } from './tx';
import type { InvoiceStatus } from './tables';
import { scopeWhere, type Scope } from '../scope';

export type InvoiceFilter = { partyId?: string; status?: InvoiceStatus[]; from?: string; to?: string };
export type InvoiceCursor = { invoiceDate: string; id: string }; // the decoded sort key; never sent as an object

export async function listInvoices(
  tx: SalesTx, scope: Scope, f: InvoiceFilter, page: { after?: InvoiceCursor; limit: number },
) {
  const rows = await tx.query.invoices.findMany({
    columns: { id: true, number: true, invoiceDate: true, status: true, grandTotal: true },
    with: { party: { columns: { id: true, name: true } } }, // read through the relation (ADR-001 §5)
    // the operators object has no sql (§4)
    where: (i, { and, or, eq, gte, lte, lt, inArray }) =>
      and(
        scopeWhere(scope, { party: i.partyId, owner: i.ownerId, entity: i.entityId }), // always present
        f.partyId ? eq(i.partyId, f.partyId) : undefined,
        f.status?.length ? inArray(i.status, f.status) : undefined,
        f.from ? gte(i.invoiceDate, f.from) : undefined,
        f.to ? lte(i.invoiceDate, f.to) : undefined,
        page.after
          ? or(
              lt(i.invoiceDate, page.after.invoiceDate),
              and(eq(i.invoiceDate, page.after.invoiceDate), lt(i.id, page.after.id)),
            )
          : undefined,
      ),
    orderBy: (i, { desc }) => [desc(i.invoiceDate), desc(i.id)],
    limit: page.limit + 1, // one extra row says whether there is a next page
  });
  const items = rows.slice(0, page.limit);
  const last = items.at(-1);
  return { items, next: rows.length > page.limit && last ? { invoiceDate: last.invoiceDate, id: last.id } : null };
}
```

```ts
// packages/lib-sales/src/services/invoices.ts
import { decodeCursor, encodeCursor } from '@radcore/lib-common'; // the paging helpers (M1-29)
import { z } from 'zod';

const InvoiceCursor = z.strictObject({ invoiceDate: z.iso.date(), id: z.uuid() }); // what the cursor must hold

export async function listInvoices(ctx: Ctx, input: ListInvoicesInput) {
  const scope = await ctx.can.scope('invoice'); // M1-17: e.g. all, these parties, or own records only
  const after = input.after ? decodeCursor(InvoiceCursor, input.after) : undefined; // bad cursor: invalid_input
  const page = await repo.listInvoices(salesTx(ctx), scope, input.filter, { after, limit: input.limit });
  return { items: page.items, next: page.next ? encodeCursor(page.next) : null };
}
```

**The cursor is an opaque string** (M1-29, decided 7 Nov): base64url of the sort key. `next` goes to the client as
that string, and the client only sends it back as `after`. It never reads or builds one. The server never trusts
it:
- `decodeCursor` checks it against the list's own schema. A cursor that doesn't decode to this list's sort key
  (malformed, or from a list with another key) is refused with 400 `invalid_input` (ADR-001 §7a).
- A cursor that does decode, even an edited one, only sets where the page starts. The scope term is applied on
  every page, so it can't reach a record outside the person's scope.

`scopeWhere` returns a condition for every kind of scope. "All" is a condition on the entity, so the scope term is
never `undefined` and a person never gets more than their scope. The indexes this needs are
`(invoice_date desc, id desc)`, plus one on `party_id` and `owner_id` (ADR-005: every foreign key has an index).

### A report read from a view (no SQL string outside the SQL zone)

Receivables ageing over the ledger. The view is defined once, in the SQL zone, and carries the columns a scope
filters on.

```ts
// packages/db/views/receivables-ageing.ts  (SQL zone: sql only as the argument of .as())
export const vReceivablesAgeing = pgView('v_receivables_ageing', {
  entityId: uuid('entity_id').notNull(), // scope columns
  partyId: uuid('party_id').notNull(),
  ownerId: uuid('owner_id'),
  notDue: numeric('not_due').notNull(),
  days1To30: numeric('days_1_30').notNull(),
```

```ts
import { vReceivablesAgeing as v } from '../../views';

export function receivablesAgeing(tx: AccountsTx, scope: Scope, limit: number) {
  return tx.select().from(v)
    .where(and(scopeWhere(scope, { party: v.partyId, owner: v.ownerId, entity: v.entityId }), gt(v.total, '0')))

}
```

## Consequences

- No SQL can arrive in a library, a route or a screen without a lint failure. No comment can switch the check off,
  and the module transaction offers no raw route even if lint missed one. Every SQL statement is in the SQL zone.
- Reports that v1 wrote as inline SQL become named views. That's more files, but each view is reviewed, carries its
  scope columns, can be tested on its own, and is shared by the screen, the export and the books check.
- Repositories and the module transaction are the seam for the Drizzle 1.0 move. Its relational-query API changes
  shape, and most of the change lands in `packages/db`.
- A lint rule on string shapes can misfire on a message that reads like SQL. The fix is to reword the message, not
  to add an exception.

## Alternatives considered

- **Prisma** (the plan's alternative to N1). Its relations API is nicer, but CHECKs, partitions and triggers would
  be hand-written migration SQL, and reports would need its typed-SQL feature. Not chosen (N1).
- **Raw SQL in repositories only.** That was v1's habit with one more folder. It doesn't meet N1.
- **CHECKs only in hand-written migrations.** This would keep the ticket's two folders literally, at the price of a
  hand-synced list between schema and migration. Rejected (§3).
- **pg-boss `send` on the request's connection** (a raw executor). It needs a driver-level `query` call outside
  `request-context.ts`. The outbox row does the same job with the query builder.
- **Lint alone as the guard.** Every new ESLint selector invites a new spelling around it. The runtime module
  transaction is the guard; lint names the mistake early.
