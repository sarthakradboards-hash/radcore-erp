# ADR-002: Drizzle ORM and data access

- Status: accepted
- Date: 2026-11-05, revised 2026-11-06 after the auditor's review
- Ticket: RAD-8 (M0-03). Covers RC-221.
- Decided by: N1 (Sarthak, 5 Nov 2026: Drizzle ORM). The coordinator accepted the SQL zone in §3 on 5 Nov.
- Builds on: [ADR-001](001-layers.md) (package layout, table ownership, the module transaction). Pairs with ADR-005
  (database conventions: CHECKs, triggers and views).

## Context

v1 used Drizzle for its schema, but its list and report routes carried their SQL inline (v1
`docs/ARCHITECTURE.md` §12, "SQL in routes"). Nothing stopped a new SQL string or a `dangerouslySetInnerHTML`, and
the Meta lead pull followed whatever "next page" URL the response contained without checking its host (RC-221).
The senior reviewer's main point about v1 was that application code should not hold SQL.

## Decision

### 1. Queries go through Drizzle, never through strings

Application code reads and writes the database in exactly two ways, always through its module transaction
(`salesTx(ctx)` and so on; ADR-001 §5):

- **Drizzle's relational queries** (`query.<table>.findMany / findFirst` with `columns`, `with`, `where`,
  `orderBy`, `limit`) for reads that follow relations.
- **Drizzle's typed query builder** (`select / insert / update / delete`, with the `eq`, `and`, `inArray`, `count`,
  `sum` and similar helpers) for everything else, including aggregates.

No SQL text appears in a library, the API, the worker or the web app. That includes the `sql` that Drizzle 0.45
hands to relational `where` and `orderBy` callbacks (`getOperators()` includes it), which is banned by syntax
(L1). Drizzle version: the 0.45 line (ADR-003). The examples below use 0.45's API.

### 2. Repositories in packages/db

Each module has its repository files in `packages/db/src/<module>/repo.ts`, next to its tables (`tables.ts`) and
relations (`relations.ts`). A repository is a plain function `(tx, scope, args) => result` built only from the
relational API and the query builder. `tx` is that module's transaction type.

- Libraries call repositories, or Drizzle directly for a one-off query on their own tables. A query that two
  services need goes into the repository, so it isn't written twice.
- A repository may join other modules' tables to read them. It writes only its own module's tables: the module
  transaction's `insert`, `update` and `delete` accept only that module's tables by type (ADR-001 §5).
- A read that returns a person's records takes the **scope** as its own argument, and ANDs it into `where`
  (worked examples below). Scope is never folded into the caller's filter.
- Repositories return numeric columns as Drizzle gives them (strings). lib-common turns them into decimals
  (ADR-005).

### 3. The SQL zone

SQL is written only in the SQL zone, which is inside `packages/db` and reviewed like code:

| Where | What | Why it must be SQL |
|---|---|---|
| `packages/db/migrations/**` | migrations generated by drizzle-kit from the schema, plus hand-written ones (`drizzle-kit generate --custom`) for triggers and functions | triggers and functions have no Drizzle declaration |
| `packages/db/views/*.ts` | one named view per file, `pgView(...).as(...)`. The query builder is used where it can express the view, `sql` where it can't (window functions, recursive CTEs). drizzle-kit generates the `CREATE VIEW` migration. | reports over ledgers (ADR-005) |
| `packages/db/src/*/tables.ts`, `packages/db/src/columns.ts` | CHECK constraints, generated columns and default expressions in table declarations: DDL only, never run as a query | Drizzle declares CHECKs with `sql`. Keeping them in the schema means drizzle-kit generates them, so schema and migration can't drift apart. |
| `packages/db/src/request-context.ts` | the one helper run at the start of each transaction. It sets the acting principal and request id for the audit triggers, and the contract's statement timeout (`set_config(..., true)`), with values passed as bound parameters, never pasted into the text. The triggers read the principal with `nullif(current_setting('app.principal', true), '')` and raise if it is missing (ADR-005, M1-12). | a session setting has no query-builder form |

The zone adds the schema files and one helper to the ticket's "migrations and views", because Drizzle declares
CHECKs in the schema with `sql`. Moving them into hand-written migrations would make two lists to keep in step.
Repositories (`repo.ts`) get no SQL.

**Applied migrations never change.** A change is a new migration (M1-07 runs them forward only). CI (M0-08) fails
when a migration file that exists on `dev` is edited, renamed or deleted, or when `migrations/meta/_journal.json`
changes other than by appending an entry with a later timestamp. Drizzle's migrator compares timestamps, not hashes,
so CI is what notices an edit.

**The runtime login isn't the owner** (M1-06). Even SQL that slipped through couldn't alter a table or switch off
an audit trigger.

### 4. Transactions: one per request, declared on the contract

- The generic handler and the job runner open the transaction (ADR-001 §6). Nothing else does. lib-platform
  exports the opener only from its `runtime` entry, which only `apps/api` and `apps/worker` may import (L7).
- **The contract declares the transaction.** `defineContract` and the job contract take a required
  `tx: { readOnly: boolean, isolation: 'read committed' | 'repeatable read', statementTimeoutMs?: number }`.
  Nothing is inferred from the method. A list is `{ readOnly: true, isolation: 'read committed' }`. A report that
  combines several queries is `{ readOnly: true, isolation: 'repeatable read' }`, so all its parts see one snapshot
  (the books check, M2-07). A write is `{ readOnly: false, isolation: 'read committed' }`.
- **Timeouts.** lib-platform's pool sets `statement_timeout`, `lock_timeout` and
  `idle_in_transaction_session_timeout` on every connection (node-postgres 8.23 supports all three), plus a pool
  wait limit. Values come from config (M1-10). A contract that needs longer, such as the books check, sets
  `statementTimeoutMs`, which `request-context.ts` applies for that transaction only. RC-080 is designed out here
  and proved in M1-08.
- **Pooler.** Connections go straight from the pool to PostgreSQL (or through a pooler in session mode). A
  transaction-mode pooler would drop those startup settings, so it isn't used (ADR-004).
- **Paging.** List contracts cap `limit` (200 at most) in lib-common's base paging schema (RC-176, M1-29).
- **Exports.** An export that may be large runs as a job, in one `{ readOnly: true, isolation: 'repeatable read' }`
  transaction, and writes the file to the file store. The person downloads it when it's ready. One snapshot means
  rows written during the export can't be skipped or repeated, and no transaction waits on a slow client.
- A nested `tx.transaction(...)` (a savepoint) is allowed only where a partial rollback is intended, with a comment
  saying why.

**No unbounded writes.** The module transaction (built in `@radcore/db/<module>`) wraps `update` and `delete`:

- `.where(cond)` throws `UnboundedWriteError` when `cond` is `undefined`. That is what `and(undefined, undefined)`
  returns when every optional filter is empty.
- Running an `update` or `delete` with no `.where()` at all also throws.
- Unit-tested with an all-empty filter. This runtime guard is the real protection; L5 is an early warning.

**Queuing a job.** A service queues a job by inserting an outbox row in its own transaction, with the query
builder on lib-platform's `jobs_outbox` table (`ctx.jobs.send` does it). The worker's relay hands committed rows to
pg-boss and deletes them. A save that rolls back leaves no row, so it queues nothing, and no raw SQL executor is
needed (M1-26).

## Lint rules (for M0-07 to add, M0-08 to run in CI)

"Server code" means `packages/**`, `apps/api/**` and `apps/worker/**`.

**Each rule has its own zone, the exact files where it is off, and nowhere else:**

| Rule | Off only in |
|---|---|
| L1 (no `sql`) | `packages/db/views/*.ts`, `packages/db/src/*/tables.ts`, `packages/db/src/columns.ts`, `packages/db/src/request-context.ts` |
| L2 (no query strings) | `packages/db/views/*.ts`, `packages/db/src/request-context.ts` |
| L3 (no raw execution) | `packages/db/src/request-context.ts` |
| L4 (no driver) | `packages/lib-platform/src/db/client.ts` |
| L9 (no table or view declarations) | `packages/db/src/*/tables.ts`, `packages/db/src/columns.ts`, `packages/db/views/*.ts` |

(`packages/db/migrations/**` holds `.sql` files, which ESLint doesn't read.)

The ESLint config holds these lists in one constant per rule (`SQL_ZONE.L1` and so on).

- **No inline overrides:** `linterOptions.noInlineConfig: true`, so an `eslint-disable` comment can't switch a rule
  off.
- **The config is tested.** An M0-07 test fails when a zone constant differs from this table. It also calls
  ESLint's `calculateConfigForFile` on a sample file outside each zone and asserts that every L-rule is at `error`
  there.
- Widening a zone means amending this ADR in a reviewed PR.

**Zone files can't leak SQL outward.** In zone files, ESLint bans exporting a `sql` template or a value built from
one. It also bans exported functions everywhere except `columns.ts` (column helpers) and `request-context.ts` (its
one helper). A unit test checks that each `columns.ts` helper returns a column builder or a CHECK definition,
never an `SQL` value a query could reuse.

| # | Rule | How | Fails when |
|---|---|---|---|
| L1 | no `sql` | ESLint `no-restricted-syntax` on any tagged template whose tag is `sql` or ends in `.sql`, any `sql.*` member (`raw`, `join`, `identifier`, `empty`), any destructured `sql` (`(t, { sql }) =>`), and any `import(...)` expression; `no-restricted-imports` of `sql` from `drizzle-orm` and `drizzle-orm/*` | server code outside the L1 zone writes SQL, including through Drizzle's `where` callback or a dynamic import |
| L2 | no query strings | ESLint `no-restricted-syntax` on `Literal` and `TemplateElement` values shaped like an SQL statement (`select … from`, `insert into`, `update … set`, `delete from`, `with … as (`, `create\|alter\|drop table\|view\|index\|trigger\|function`, `truncate`, `grant`), case-insensitive | server code holds a string that is a query (a message that trips it gets reworded) |
| L3 | no raw execution | ESLint `no-restricted-syntax` on calls to `.execute(`, `.unsafe(` or `.query(` with arguments | server code runs SQL text through the driver or Drizzle |
| L4 | no driver | ESLint `no-restricted-imports` with patterns `pg`, `pg-*`, `postgres`, `@electric-sql/*`, `drizzle-orm/node-postgres`, `drizzle-orm/pglite`, `drizzle-orm/postgres-js` | anything else opens its own connection |
| L5 | early warning on updates and deletes | `eslint-plugin-drizzle` `enforce-update-with-where`, `enforce-delete-with-where` | an obvious `delete(table)` or `update(table).set(...)` with no `where`. The runtime guard in §4 catches the rest. |
| L6 | no raw HTML | `react/no-danger` (error) in `apps/web`; `no-restricted-syntax` everywhere on assignments to `innerHTML` / `outerHTML`, calls to `insertAdjacentHTML`, `document.write`, `document.writeln` and `setHTMLUnsafe`, and the JSX attribute `srcDoc` | any way of putting unparsed HTML on a page |
| L7 | only the apps open transactions | dependency-cruiser: `@radcore/lib-platform/runtime` imported only from `apps/api` and `apps/worker` | a library opens its own transaction |
| L8 | outside calls go through the guarded client | ESLint `no-restricted-globals` (`fetch`, `WebSocket`, `XMLHttpRequest`), `no-restricted-properties` (`globalThis.fetch`), `no-restricted-imports` with patterns `undici`, `axios`, `got`, `node-fetch`, `ws`, `http`, `https`, `http2`, `net`, `tls` and their `node:` forms, in server code except `packages/lib-platform/src/http/outbound.ts` | server code makes a network call any other way |
| L9 | tables and views are declared only in packages/db | `no-restricted-imports` of `pgTable`, `pgView`, `pgMaterializedView`, `pgSchema` and `pgEnum` from `drizzle-orm/pg-core` | anything outside the L9 zone declares its own handle on a table or view (another module's, or a system one such as `pg_stat_activity`) |

Every rule has one violating fixture per clause in `tools/boundary-fixtures/` (as for ADR-001's rules), checked on
every CI run.

### The outbound client (L8)

All outside HTTP from server code goes through one client, `createOutbound({ name, allowedOrigins, credential })`
in `packages/lib-platform/src/http/outbound.ts`. lib-integrations and the alert sender both use it.

- **Origins.** Each client is created with the exact origins it may reach, for example Meta:
  `allowedOrigins: ['https://graph.facebook.com']`. An origin taken from settings, such as a Shopify shop, is
  checked against a fixed pattern when it is configured (`^[a-z0-9-]+\.myshopify\.com$`).
- **Every request is checked before it's sent**, including a URL taken from a response (Meta's `paging.next`,
  Shopify's `Link` header):
  - the URL is parsed with the WHATWG `URL` class;
  - it must be `https:`, on the default port, with no username or password;
  - its origin must be in the list exactly, with no suffix or substring match;
  - the request is sent to the parsed `url.href`.
- **Credentials.** The client's credential goes in the `Authorization` header, never in the URL (M1-24). Before a
  response URL is used, any credential parameter the client names (for Meta, `access_token`, which Graph API
  paging links do carry) is removed from it.
- **Logs** show only the origin and path, never the query or headers.
- **Redirects** are followed by hand (`redirect: 'manual'`), at most 3 hops.
  - Each `Location` is resolved with `new URL(location, current)` and passes the same check.
  - If a redirect crosses to another allowed origin, `Authorization` is dropped.
- **Addresses.** The host's resolved address is checked: a private, loopback, link-local or metadata address
  (10/8, 172.16/12, 192.168/16, 127/8, 169.254/16, ::1, fc00::/7, fe80::/10) is refused. The connection is pinned
  to the checked address, so DNS can't change between the check and the connect.
- **Limits.** Each request has a timeout (10 s by default) and a response-size limit (10 MB by default).
- **Proof**, a unit test with a mocked transport, in the ticket that builds the client and again in the Meta
  lead-pull ticket. Allowed:
  - `https://graph.facebook.com/v21.0/123/leads?after=X&access_token=T` is sent once, to a URL without
    `access_token`, with the token in the header.

  Refused, with the transport mock called **zero** times:
  - `https://graph.facebook.com.evil.example/`
  - `http://graph.facebook.com/`
  - `https://user:pass@graph.facebook.com/`
  - `https://graph.facebook.com:8443/`
  - a host resolving to `127.0.0.1`

  A `302` from an allowed page to `https://evil.example/` makes exactly one transport call (the first hop) and is
  then refused. A redirect chain of 4 hops is refused at the 4th.

## Worked examples

Names such as `ctx.can` and `scopeWhere` are illustrative; the M1 tickets fix the exact APIs. What the examples
fix is the shape:
- no SQL string;
- the module transaction;
- scope as its own argument;
- the relation read;
- keyset paging.

### A list with filter, scope and paging (no SQL string)

Invoices for one screen, filtered by party, status and dates, newest first, with keyset paging. Each page is one
indexed range read, never a count of the whole ledger (RC-176).

```ts
// packages/db/src/sales/repo.ts
import type { SalesTx } from './tx';
import type { InvoiceStatus } from './tables';
import { scopeWhere, type Scope } from '../scope';

export type InvoiceFilter = { partyId?: string; status?: InvoiceStatus[]; from?: string; to?: string };
export type InvoiceCursor = { invoiceDate: string; id: string };

export async function listInvoices(
  tx: SalesTx, scope: Scope, f: InvoiceFilter, page: { after?: InvoiceCursor; limit: number },
) {
  const rows = await tx.query.invoices.findMany({
    columns: { id: true, number: true, invoiceDate: true, status: true, grandTotal: true },
    with: { party: { columns: { id: true, name: true } } }, // read through the relation (ADR-001 §5)
    where: (i, { and, or, eq, gte, lte, lt, inArray }) =>
      and(
        scopeWhere(scope, { party: i.partyId, owner: i.ownerId, entity: i.entityId }), // always present
        f.partyId ? eq(i.partyId, f.partyId) : undefined,
        f.status?.length ? inArray(i.status, f.status) : undefined,
        f.from ? gte(i.invoiceDate, f.from) : undefined,
        f.to ? lte(i.invoiceDate, f.to) : undefined,
        page.after
          ? or(
              lt(i.invoiceDate, page.after.invoiceDate),
              and(eq(i.invoiceDate, page.after.invoiceDate), lt(i.id, page.after.id)),
            )
          : undefined,
      ),
    orderBy: (i, { desc }) => [desc(i.invoiceDate), desc(i.id)],
    limit: page.limit + 1, // one extra row says whether there is a next page
  });
  const items = rows.slice(0, page.limit);
  const last = items.at(-1);
  return { items, next: rows.length > page.limit && last ? { invoiceDate: last.invoiceDate, id: last.id } : null };
}
```

```ts
// packages/lib-sales/src/services/invoices.ts
export async function listInvoices(ctx: Ctx, input: ListInvoicesInput) {
  const scope = await ctx.can.scope('invoice'); // M1-17: e.g. all, these parties, or own records only
  return repo.listInvoices(salesTx(ctx), scope, input.filter, { after: input.after, limit: input.limit });
}
```

`scopeWhere` returns a condition for every kind of scope. "All" is a condition on the entity, so the scope term is
never `undefined` and a person never gets more than their scope. The indexes this needs are
`(invoice_date desc, id desc)`, plus one on `party_id` and `owner_id` (ADR-005: every foreign key has an index).

### A report read from a view (no SQL string outside the SQL zone)

Receivables ageing over the ledger. The view is defined once, in the SQL zone, and carries the columns a scope
filters on.

```ts
// packages/db/views/receivables-ageing.ts  (SQL zone: the definition)
export const vReceivablesAgeing = pgView('v_receivables_ageing', {
  entityId: uuid('entity_id').notNull(), // scope columns
  partyId: uuid('party_id').notNull(),
  ownerId: uuid('owner_id'),
  notDue: numeric('not_due').notNull(),
  days1To30: numeric('days_1_30').notNull(),
  days31To60: numeric('days_31_60').notNull(),
  over60: numeric('over_60').notNull(),
  total: numeric('total').notNull(),
}).as(sql`/* reviewed in this file; reads the invoice-outstanding view and buckets by due date */ ...`);
```

```ts
// packages/db/src/accounts/repo.ts  (no SQL: the view is queried like a table)
import { and, desc, gt } from 'drizzle-orm';
import { vReceivablesAgeing as v } from '../../views/receivables-ageing';

export function receivablesAgeing(tx: AccountsTx, scope: Scope, limit: number) {
  return tx.select().from(v)
    .where(and(scopeWhere(scope, { party: v.partyId, owner: v.ownerId, entity: v.entityId }), gt(v.total, '0')))
    .orderBy(desc(v.total)).limit(limit);
}
```

```ts
// packages/lib-accounts/src/contract.ts
export const receivablesAgeing = defineContract({
  method: 'GET', path: '/accounts/reports/receivables-ageing', auth: 'session', perm: 'accounts:reports',
  tx: { readOnly: true, isolation: 'repeatable read' },
  input: AgeingInput, output: AgeingRows,
});

// packages/lib-accounts/src/services/reports.ts
export async function receivablesAgeing(ctx: Ctx, input: AgeingInput) {
  const scope = await ctx.can.scope('receivable'); // a salesperson may see only their own parties
  return repo.receivablesAgeing(accountsTx(ctx), scope, input.limit);
}
```

## Consequences

- No SQL can arrive in a library, a route or a screen without a lint failure, and no comment can switch the check
  off. Every SQL statement is in the SQL zone.
- Reports that v1 wrote as inline SQL become named views. That's more files, but each view is reviewed, carries its
  scope columns, can be tested on its own, and is shared by the screen, the export and the books check.
- Repositories are the seam for the Drizzle 1.0 move. Its relational-query API changes shape, and most of the
  change lands in `packages/db`.
- A lint rule on string shapes can misfire on a message that reads like SQL. The fix is to reword the message, not
  to add an exception.

## Alternatives considered

- **Prisma** (the plan's alternative to N1). Its relations API is nicer, but CHECKs, partitions and triggers would
  be hand-written migration SQL, and reports would need its typed-SQL feature. Not chosen (N1).
- **Raw SQL in repositories only.** That was v1's habit with one more folder. It doesn't meet N1.
- **CHECKs only in hand-written migrations.** This would keep the ticket's two folders literally, at the price of a
  hand-synced list between schema and migration. Rejected (§3).
- **pg-boss `send` on the request's connection** (a raw executor). It needs a driver-level `query` call outside
  `request-context.ts`. The outbox row does the same job with the query builder.
