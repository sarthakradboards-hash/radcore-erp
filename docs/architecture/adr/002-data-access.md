# ADR-002: Drizzle ORM and data access

- Status: accepted
- Date: 2026-11-05
- Ticket: RAD-8 (M0-03). Covers RC-221.
- Decided by: N1 (Sarthak, 5 Nov 2026: Drizzle ORM).
- Builds on: [ADR-001](001-layers.md) (package layout and table ownership). Pairs with ADR-005 (database
  conventions: CHECKs, triggers and views).

## Context

v1 used Drizzle for its schema, but its list and report routes carried their SQL inline (v1
`docs/ARCHITECTURE.md` §12, "SQL in routes"). Nothing stopped a new SQL string or a `dangerouslySetInnerHTML`, and
the Meta lead pull followed whatever "next page" URL the response contained without checking its host (RC-221).
The senior reviewer's main point about v1 was that application code should not hold SQL.

## Decision

### 1. Queries go through Drizzle, never through strings

Application code reads and writes the database in exactly two ways:

- **Drizzle's relational queries** (`ctx.tx.query.<table>.findMany / findFirst` with `columns`, `with`, `where`,
  `orderBy`, `limit`) for reads that follow relations.
- **Drizzle's typed query builder** (`select / insert / update / delete`, with the `eq`, `and`, `inArray`, `count`,
  `sum` and similar helpers) for everything else, including aggregates.

No SQL text appears in a library, the API, the worker or the web app: no `sql` template, no `.execute(...)`, no
driver `query()` call, no string that is a query. Drizzle version: the 0.45 line, the latest stable release (the
exact version and the move to 1.0 are decided in ADR-003). The examples below use 0.45's API.

### 2. Repositories in packages/db

Each module has its repository files in `packages/db/src/<module>/repo.ts`, next to its tables
(`tables.ts`) and relations (`relations.ts`). A repository is a plain function `(tx, args) => result` built only
from the relational API and the query builder.

- Libraries call repositories, or Drizzle directly for a one-off query on their own tables. A query that two
  services need goes into the repository, so it isn't written twice.
- A repository may join other modules' tables to read them. It writes only its own module's tables
  (ADR-001 §5). Review enforces this inside packages/db; the import rule D7 enforces it everywhere else.
- Repositories return numeric columns as Drizzle gives them (strings). lib-common turns them into decimals
  (ADR-005).

### 3. Where SQL is allowed

SQL is written in four places, all inside `packages/db`, each reviewed like code:

| Where | What | Why it must be SQL |
|---|---|---|
| `packages/db/migrations/*.sql` | migrations generated by drizzle-kit from the schema, plus hand-written ones (`drizzle-kit generate --custom`) for triggers and functions | triggers and functions have no Drizzle declaration |
| `packages/db/views/*.ts` | one named view per file, `pgView(...).as(...)`. The query builder is used where it can express the view, `sql` where it cannot (window functions, recursive CTEs). drizzle-kit generates the `CREATE VIEW` migration from it. | reports over ledgers (ADR-005) |
| `packages/db/src/<module>/tables.ts`, `packages/db/src/columns.ts` | CHECK constraints, generated columns and default expressions in table declarations: DDL only, never run as a query | Drizzle declares CHECKs with `sql`. Keeping them in the schema means drizzle-kit generates them, so schema and migration can't drift apart. |
| `packages/db/src/request-context.ts` | the one helper that sets the acting user and request id for the audit triggers at the start of each transaction (`set_config(..., true)`), with values passed as bound parameters, never pasted into the text | a session setting has no query-builder form |

This adds the schema files and one helper to the ticket's "migrations and views". The reason is that Drizzle
declares CHECKs in the schema with `sql`. Moving them into hand-written migrations would make two lists to keep in
step. Repositories (`repo.ts`) get no SQL.

A migration that has reached `dev` is never edited. A change is a new migration (M1-07 runs them forward only).

### 4. Transactions: one per request, passed as ctx.tx

- The generic handler (ADR-001 §6) and the job runner open the transaction. Nothing else does. lib-platform
  exports the opener only from its `runtime` entry, which only `apps/api` and `apps/worker` may import (rule L7
  below).
- Every service receives it as `ctx.tx` and passes it on. There is no global `db` object to import.
- A read-only contract (`GET`) runs `accessMode: 'read only'`. A report that combines several queries runs
  `isolationLevel: 'repeatable read'` and read only, so all its parts see one snapshot (the books check, M2-07,
  needs this).
- Timeouts are set on every connection by lib-platform's pool: `statement_timeout`, `lock_timeout` and
  `idle_in_transaction_session_timeout` (node-postgres 8.23 supports all three as connection options), plus a pool
  wait limit. Values come from config (M1-10). RC-080 is designed out here and proved in M1-08.
- A nested `ctx.tx.transaction(...)` (a savepoint) is allowed only where a partial rollback is the intended
  behaviour, with a comment saying why.
- A streamed export (M1-29) reads page by page with the keyset cursor below, each page in its own short read-only
  transaction. No transaction stays open while a slow client downloads, so the idle timeout never cuts an export
  short.

## Lint rules (for M0-07 to add, M0-08 to run in CI)

"Server code" means `packages/**`, `apps/api/**` and `apps/worker/**`. Each rule must fail CI, and M0-07 proves
each one with a throwaway commit that breaks it.

**The SQL zone is exactly these globs, and nothing else:**

```
packages/db/migrations/**            (SQL files; drizzle-kit output and --custom migrations)
packages/db/views/*.ts
packages/db/src/*/tables.ts
packages/db/src/columns.ts
packages/db/src/request-context.ts
```

The ESLint config holds them in one constant, `SQL_ZONE`. It is the only place L1 to L3 are switched off. M0-07
adds a test that fails when `SQL_ZONE` differs from this list, so widening the zone means amending this ADR in a
reviewed PR. `repo.ts` files are outside the zone.

| # | Rule | How | Fails when |
|---|---|---|---|
| L1 | no `sql` template outside the SQL zone | ESLint `no-restricted-imports` with `importNames: ['sql']` on `drizzle-orm` (and any `drizzle-orm/*` path that re-exports it), turned off only in the SQL zone | a file outside the zone imports `sql` |
| L2 | no query strings in server code | ESLint `no-restricted-syntax` on `Literal` and `TemplateElement` values matching an SQL statement shape (`select … from`, `insert into`, `update … set`, `delete from`, `with … as (`, `create\|alter\|drop table\|view\|index\|trigger\|function`, `truncate`, `grant`), case-insensitive, outside the SQL zone | server code holds a string that is a query (a message that trips it gets reworded) |
| L3 | no raw execution | ESLint `no-restricted-syntax` on calls to `.execute(`, `.unsafe(` or a driver `.query(` outside the SQL zone | server code runs SQL text through the driver or Drizzle |
| L4 | no driver outside the pool | ESLint `no-restricted-imports` for `pg`, `postgres`, `@electric-sql/pglite`, `drizzle-orm/node-postgres`, `drizzle-orm/pglite` except in lib-platform's database client file | anything else opens its own connection |
| L5 | updates and deletes have a `where` | `eslint-plugin-drizzle`: `enforce-update-with-where`, `enforce-delete-with-where` (object names `tx`, `db`) | `tx.delete(table)` or `tx.update(table).set(...)` with no `where` |
| L6 | no raw HTML | ESLint `react/no-danger` (error, no exceptions) in `apps/web`, and `no-restricted-syntax` on assignments to `innerHTML` / `outerHTML` everywhere | any use of `dangerouslySetInnerHTML` or an `innerHTML` assignment |
| L7 | only the apps open transactions | dependency-cruiser: `@radcore/lib-platform/runtime` imported only from `apps/api` and `apps/worker` | a library opens its own transaction |
| L8 | outside calls go through the guarded client | ESLint `no-restricted-globals` (`fetch`) and `no-restricted-imports` (`undici`, `axios`, `got`, `node:http`, `node:https`, `http`, `https`) in server code, except lib-platform's outbound client file | server code makes an HTTP call any other way |

### The outbound client and paging URLs (L8)

All outside HTTP from server code goes through one client in lib-platform (`createOutbound({ name, allowedOrigins })`).
lib-integrations and the alert sender both use it.

- Each client is created with the exact origins it may reach, for example Meta:
  `allowedOrigins: ['https://graph.facebook.com']`.
- Every request is checked before it is sent, including a URL taken from a response (Meta's `paging.next`,
  Shopify's `Link` header). The URL is parsed with the WHATWG `URL` class. It must be `https:`, its origin must
  be in the list exactly (no suffix or substring match), and it must carry no username or password. Otherwise the
  request is refused and logged.
- Redirects are not followed automatically (`redirect: 'manual'`). A redirect is followed only if its target
  passes the same check.
- Tokens travel in headers, never in the URL (M1-24), so a paging URL doesn't carry one.
- Proof, a unit test in the ticket that builds the outbound client, run again in the Meta lead-pull ticket: a
  response whose `paging.next` points at `https://graph.facebook.com.evil.example/`,
  `http://graph.facebook.com/` or `https://user:pass@graph.facebook.com/` is refused before any request leaves
  the server.

## Worked examples

Names such as `ctx.can(...).narrow(...)` are illustrative. The M1 tickets fix the exact APIs. What the examples
fix is the shape: no SQL string, the relation read, and keyset paging.

### A list with filter and paging (no SQL string)

Invoices for one screen, filtered by party, status and dates, newest first, with keyset paging. Each page is one
indexed range read, never a count of the whole ledger (RC-176).

```ts
// packages/db/src/sales/repo.ts
import type { Tx } from '../tx';
import type { InvoiceStatus } from './tables';

export type InvoiceFilter = { partyId?: string; status?: InvoiceStatus[]; from?: string; to?: string };
export type InvoiceCursor = { invoiceDate: string; id: string };

export async function listInvoices(tx: Tx, f: InvoiceFilter, page: { after?: InvoiceCursor; limit: number }) {
  const rows = await tx.query.invoices.findMany({
    columns: { id: true, number: true, invoiceDate: true, status: true, grandTotal: true },
    with: { party: { columns: { id: true, name: true } } }, // read through the relation (ADR-001 §5)
    where: (i, { and, or, eq, gte, lte, lt, inArray }) =>
      and(
        f.partyId ? eq(i.partyId, f.partyId) : undefined,
        f.status?.length ? inArray(i.status, f.status) : undefined,
        f.from ? gte(i.invoiceDate, f.from) : undefined,
        f.to ? lte(i.invoiceDate, f.to) : undefined,
        page.after
          ? or(
              lt(i.invoiceDate, page.after.invoiceDate),
              and(eq(i.invoiceDate, page.after.invoiceDate), lt(i.id, page.after.id)),
            )
          : undefined,
      ),
    orderBy: (i, { desc }) => [desc(i.invoiceDate), desc(i.id)],
    limit: page.limit + 1, // one extra row says whether there is a next page
  });
  const items = rows.slice(0, page.limit);
  const last = items.at(-1);
  return { items, next: rows.length > page.limit && last ? { invoiceDate: last.invoiceDate, id: last.id } : null };
}
```

```ts
// packages/lib-sales/src/services/invoices.ts
export async function listInvoices(ctx: Ctx, input: ListInvoicesInput) {
  const scope = await ctx.can('sales:read'); // record scope (M1-17): may narrow the filter, never widen it
  return repo.listInvoices(ctx.tx, scope.narrow(input.filter), { after: input.after, limit: input.limit });
}
```

The index this needs is `(invoice_date desc, id desc)` plus one on `party_id` (ADR-005: every foreign key has an
index).

### A report read from a view (no SQL string outside packages/db/views)

Receivables ageing over the ledger. The view is defined once, in the SQL zone, and drizzle-kit generates its
`CREATE VIEW` migration.

```ts
// packages/db/views/receivables-ageing.ts  (SQL zone: the definition)
export const vReceivablesAgeing = pgView('v_receivables_ageing', {
  partyId: uuid('party_id').notNull(),
  notDue: numeric('not_due').notNull(),
  days1To30: numeric('days_1_30').notNull(),
  days31To60: numeric('days_31_60').notNull(),
  over60: numeric('over_60').notNull(),
  total: numeric('total').notNull(),
}).as(sql`/* reviewed in this file; reads the invoice-outstanding view and buckets by due date */ ...`);
```

```ts
// packages/db/src/accounts/repo.ts  (no SQL: the view is queried like a table)
import { desc, gt } from 'drizzle-orm';
import { vReceivablesAgeing } from '../../views/receivables-ageing';

export function receivablesAgeing(tx: Tx, limit: number) {
  return tx.select().from(vReceivablesAgeing).where(gt(vReceivablesAgeing.total, '0'))
    .orderBy(desc(vReceivablesAgeing.total)).limit(limit);
}
```

```ts
// packages/lib-accounts/src/services/reports.ts
export function receivablesAgeing(ctx: Ctx, input: AgeingInput) {
  return repo.receivablesAgeing(ctx.tx, input.limit); // the route runs it read only, repeatable read (§4)
}
```

## Consequences

- No SQL can arrive in a library, a route or a screen without a lint failure, so reviewers can find every SQL
  statement in four folders.
- Reports that v1 wrote as inline SQL become named views. That's more files, but each view is reviewed, can be
  tested on its own, and is shared by the screen, the export and the books check.
- Repositories are the seam for the Drizzle 1.0 move. Its relational-query API changes shape, and most of the
  change lands in `packages/db`.
- A lint rule on string shapes can misfire on a message that reads like SQL. The fix is to reword the message,
  not to add an exception.

## Alternatives considered

- **Prisma** (the plan's alternative to N1). Its relations API is nicer, but CHECKs, partitions and triggers would
  be hand-written migration SQL, and reports would need its typed-SQL feature. Not chosen (N1).
- **Raw SQL in repositories only.** That was v1's habit with one more folder. It doesn't meet N1.
- **CHECKs only in hand-written migrations.** This would keep the ticket's two folders literally, at the price of a
  hand-synced list between schema and migration. Rejected (§3).
